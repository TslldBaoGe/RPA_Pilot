# 在线更新部署指南

面向前提：**内网服务器能访问 github.com**、代码仓库为**公有仓库**、更新源用**内网域名**。

---

## 1. 整体结构

```
你的电脑                 GitHub                      内网服务器                 同事的电脑
────────                ──────                      ──────────                 ──────────
git push  ──────────►   仓库 main 分支
                         │
                         │ 打标签触发
                         ▼
                        GitHub Actions
                        (windows runner)
                        构建安装包
                         │
                         │ 挂成 Release 附件
                         ▼
                        Release v0.1.4  ──────►   计划任务每 N 分钟
                        ├ latest.yml               跑 sync-updates.ps1
                        ├ ....exe                  下载附件 → 写进 IIS 目录
                        └ ....blockmap             （保留最近 3 个版本）      ──►  RPA_Pilot.exe
                                                                                  自动检查更新
```

**为什么让服务器「拉」而不是「推」**：拉取只需要出站 HTTPS，内网不用开任何入站端口，
防火墙那边什么都不用改。GitHub 的云端 runner 也够不到你的内网，推不了。

---

## 2. 一次性准备（5 步）

### 步骤 1：把更新源地址改成真实的（⚠️ 最容易漏）

打开 `electron-builder.yml`，把 `publish.url` 改成你们真实的更新目录地址：

```yaml
publish:
  provider: generic
  url: http://updates.你的内网域名/rpa-pilot/     # ← 改这里，必须以 / 结尾
```

**必须重新打包才会生效** —— 这个地址是打包时写进安装包内 `resources\app-update.yml` 的，
改配置文件不会影响已经发出去的安装包。

改完先跑一次体检，它会拦住占位地址、`127.0.0.1`、缺结尾斜杠、UNC 路径：

```bash
pnpm release:check
```

> 这道检查是为了防止一个真实踩过的坑：本机联调用的 `http://127.0.0.1:8787/`
> 被当成正式版本发出去，结果所有同事的客户端都去连自己的本机，更新永远失败，
> 而且从安装包上根本看不出来。

### 步骤 2：建 GitHub 仓库并推代码

```bash
cd D:\RPA_Pilot
git init
git add .
git commit -m "RPA_Pilot：Python 任务管理客户端"

# 在 GitHub 上建好空仓库后（不要勾选自动生成 README）
git remote add origin https://github.com/你的账号/rpa-pilot.git
git branch -M main
git push -u origin main
```

推送前确认 `.gitignore` 已经排除掉不该进仓库的东西：
`node_modules/`、`out/`、`out-installer/`、`updates/`、`.cache/`、`data/`、`logs/`。
（本仓库的 `.gitignore` 已配好。）

### 步骤 3：服务器上准备更新目录

1. 在内网 Web 服务器上建一个能被访问到的目录，例如 `D:\inetpub\wwwroot\rpa-pilot`。
2. 在该目录下放一个 `web.config`，**这一步不能省**：

```xml
<?xml version="1.0" encoding="UTF-8"?>
<configuration>
  <system.webServer>
    <staticContent>
      <!-- .yml 和 .blockmap 在 IIS 默认 MIME 表里没有映射，不配就是 404 -->
      <mimeMap fileExtension=".yml" mimeType="text/yaml" />
      <mimeMap fileExtension=".blockmap" mimeType="application/octet-stream" />
    </staticContent>
    <directoryBrowse enabled="false" />
  </system.webServer>
</configuration>
```

> **最常见的故障就是这个**：`latest.yml` 请求返回 404，客户端表现为「检查更新一直失败」。
> 如果 IIS 报「重复项」错误，说明该映射已存在，把那行删掉即可。
> 也可以用命令行配置：`appcmd set config /section:staticContent /+"[fileExtension='.yml',mimeType='text/yaml']"`

3. 确认应用池身份对该目录有**读**权限，同步脚本的运行账号有**写**权限。

### 步骤 4：部署拉取脚本 + 计划任务

把 `scripts/sync-updates.ps1` 拷到服务器上（例如 `C:\RPA-Pilot-Sync\`），手动跑一次确认能通：

```powershell
# 只看 GitHub 上现在是什么版本，不下载
.\sync-updates.ps1 -Repo 你的账号/rpa-pilot -TargetDir D:\inetpub\wwwroot\rpa-pilot -CheckOnly

# 真同步一次
.\sync-updates.ps1 -Repo 你的账号/rpa-pilot -TargetDir D:\inetpub\wwwroot\rpa-pilot
```

确认无误后注册计划任务，每 15 分钟跑一次：

```powershell
$action  = New-ScheduledTaskAction -Execute 'powershell.exe' `
  -Argument '-NoProfile -ExecutionPolicy Bypass -File C:\RPA-Pilot-Sync\sync-updates.ps1 -Repo 你的账号/rpa-pilot -TargetDir D:\inetpub\wwwroot\rpa-pilot'
$trigger = New-ScheduledTaskTrigger -Once -At (Get-Date) `
  -RepetitionInterval (New-TimeSpan -Minutes 15)
Register-ScheduledTask -TaskName 'RPA_Pilot 更新包同步' -Action $action -Trigger $trigger `
  -RunLevel Highest -User 'SYSTEM'
```

日志默认写在 `%LOCALAPPDATA%\RPA-Pilot-UpdateSync\sync-updates.log`，
SYSTEM 账号下就是 `C:\Windows\System32\config\systemprofile\AppData\Local\...`。
建议显式指定 `-LogFile`，例如 `-LogFile D:\RPA-Pilot-Sync\sync.log`。

### 步骤 5：发第一个包给同事

按第 3 节发一次版，然后用生成的安装包发给同事。
**同事装的就是带正确更新源的版本，之后所有升级都自动完成。**

> ⚠️ 在此之前的任何安装包（更新源是 `127.0.0.1`）**都不能发**，必须重新打包。

## 3. 日常发版流程

```bash
# 1) 日常开发照常推代码
git add . && git commit -m "..." && git push

# 2) 要发版时打个标签（版本号写进标签里）
git tag v0.1.5
git push origin v0.1.5
```

打完标签之后全自动：

| 谁 | 做什么 |
|---|---|
| GitHub Actions | 检出代码 → 写入版本号 → 体检 → 类型检查 → 构建 → **校验产物里的更新源** → 发 Release |
| 内网服务器 | 15 分钟内的计划任务发现新版本 → 下载 3 个文件 → 写进 IIS 目录 → 清理过老版本 |
| 同事的客户端 | 4 小时内（或启动后 25 秒）自动发现 → 后台静默下载 → 提示「新版本已就绪」→ 用户点安装 → 静默升级并重启 |

也可以在 Actions 页面手动触发（`workflow_dispatch`），填版本号即可。

**版本号只有一个来源：git 标签。** CI 会把它写进 `package.json`，
保证安装包版本、`latest.yml` 里的版本、界面显示的版本三者一致
（不一致会导致 electron-updater 判断错）。

## 4. 回滚

**electron-updater 不会降级**，所以回滚不是「把 `latest.yml` 换回旧版本」，而是：

```bash
# 把旧版本的代码以更高的版本号重新发布
git checkout v0.1.4            # 回到出问题的版本之前
git checkout -b hotfix/rollback
# 把 package.json 的版本号改高，例如 0.1.5
git commit -am "回滚到 0.1.4 的行为，以 0.1.5 发布"
git tag v0.1.5 && git push origin v0.1.5
```

`sync-updates.ps1` 默认保留最近 3 个安装包（`-Keep`），所以旧包里还有历史版本可用。

## 5. 排错清单

| 现象 | 原因与处理 |
|---|---|
| 客户端「检查更新」报 404 | **IIS 没配 `.yml` 的 MIME 映射**，见步骤 3。先手动 `Invoke-WebRequest http://更新地址/latest.yml` 验证 |
| 客户端报无法连接/超时 | 域名解析不了，或服务器/防火墙不放行。在同事机器上跑 `Test-NetConnection updates.你的域名 -Port 80` |
| 检查更新一直成功但总提示已是最新 | 服务器上的 `latest.yml` 还是旧版本 —— 看同步脚本日志，多半是计划任务没跑或 GitHub 上还没发 Release |
| 下载安装包失败 | 服务器上文件不完整。重跑同步脚本，或加 `-Force` 强制重下 |
| 安装包下载后校验失败 | 服务器上的文件与 `latest.yml` 里的 sha512 不匹配。删掉该版本重新同步 |
| 同事装了但从不提示更新 | 他装的是**旧安装包**（更新源指向 `127.0.0.1`）。让他换成最新安装包重装 |
| 内网用自签 HTTPS 证书 | Electron 会拒绝下载（更新请求不走页面，`certificate-error` 拦不住）。改用受信任的内网 CA，或先走 HTTP |
| 更新日志在哪 | 客户端机器：`%APPDATA%\rpa-pilot\update.log`；启动诊断：同目录 `boot.log` |

## 6. 几个必须知道的边界

**1. 客户端不在内网时更新会失败，但软件照常用。**
服务器连不上时只在 `update.log` 记一条、界面显示原因，应用功能不受影响，4 小时后自动重试。
要让出差/外网的同事也能更新，得给更新源开公网入口 —— 那是另一个安全决策，不在本方案内。

**2. 公有仓库意味着源码是公开的。**
这是一套公司内部业务工具。如果业务逻辑不宜公开，请改成私有仓库：
- Actions 仍可用，但**私有仓库的 Windows runner 按 2 倍分钟数计费**（免费额度 2000 分钟/月 ≈ 1000 分钟 Windows 构建，每次约 5 分钟）
- 拉取脚本需要加 Token：设环境变量 `RPA_PILOT_GITHUB_TOKEN`（脚本已支持），
  不要把令牌明文写进脚本；计划任务里用 `-Token` 传参也会留在任务定义中，优先用环境变量或凭据管理器

**3. 更新目录的写权限要收紧。**
不签名的话，**谁能写那个目录谁就能给所有客户端推任意代码**。
`latest.yml` 里的 sha512 只保证传输没坏，不保证来源可信。

**4. 客户端本身是容错的。**
更新系统出任何问题都不会导致软件打不开 —— 更新检查在启动 25 秒后才在后台进行，
失败只记日志，不影响任务执行和定时调度。
